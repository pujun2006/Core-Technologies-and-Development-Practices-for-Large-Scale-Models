在自然语言处理与大模型训练/推理中，动态分词（Dynamic Tokenization / Dynamic Padding）**与**序列截断（Sequence Truncation）是解决“自然文本长度参差不齐”与“模型输入序列长度受限（如上下文窗口、显存上限）”之间矛盾的两项核心工程技术。

简单来说：**截断负责处理“太长的句子”（超上限裁剪），动态填充与在线/动态分词负责处理“参差不齐的句子”（按需对齐、少算废 Token）**。

---

### 一、 什么是“动态分词”？

在工程语境中，“动态分词”通常包含两个密切相关的层面：

1. **动态填充（Dynamic Padding，最常见）**：
* 不同于整份数据集预先统一补齐到全局 `max_length`（如 `512`），动态填充是在 `DataLoader` 组 Batch 时，**仅将当前 Batch 内的样本对齐到该 Batch 的最长序列长度**。
* **好处**：若某批次最长句子只有 `28` 个 token，张量形状就是 `(batch_size, 28)` 而不是 `(batch_size, 512)`。由于 Transformer 注意力计算与显存占用随序列长度近似呈平方级增长，动态填充能显著降低显存峰值并加快训练与推理吞吐。


2. **训练/预处理阶段的动态切分与长度桶（Bucket Batching）**：
* 在数据流式加载或训练过程中，按需对文本分词，甚至先按长度分桶再组 Batch，使同一 Batch 内的句子长度尽量接近，进一步减少 `[PAD]` 比例。
* 在部分分词器/训练策略中，也会结合动态采样、滑动窗口或文档拼接（Packing）来提升上下文利用率。

### 二、 序列截断（Sequence Truncation）的原理与策略

当序列长度超过模型允许的最大长度或设定的 `max_length` 时，必须进行截断，否则会触发位置编码越界或显存溢出（OOM）。

#### 1. 截断方向与位置

* **右侧截断（尾部截断，默认最常见）**：保留开头部分，裁剪末尾多余 token。适合新闻导语、标题/摘要前段、常规分类文本。
* **左侧截断（头部截断）**：保留结尾部分，裁剪开头 token。在**对话历史、日志尾部或生成式任务**中非常关键——因为最新一轮提问或最近上下文往往在末尾，丢掉早期历史比丢掉最新指令更安全。
* **中间/首尾保留截断**：部分长文本或检索/问答场景会保留开头与结尾，裁剪中间冗余段落。

#### 2. 多段文本的截断策略（如句对/上下文+问题）

当输入包含两段文本（如 `text_a` 和 `text_b`，常见于自然语言推理、问答、检索排序）时，常见的截断策略包括：

* **`longest_first`（默认）**：优先从较长的一段中逐步裁剪，直到总长度满足上限，尽量平衡两段信息的完整性。
* **`only_first` / `only_second**`：只允许截断第一段或第二段（例如在问答中，宁可截断长背景段落，也尽量完整保留问题）。

### 三、 关键协同机制：`attention_mask` 与特殊 Token

无论是动态填充还是序列截断，都必须与 **`attention_mask`** 和 **特殊标记（Special Tokens）** 协同工作：

1. **`attention_mask` 掩码对齐**：
* 真实有效 token 对应 `1`，填充位 `[PAD]` 对应 `0`。
* 自注意力计算时，掩码位置会被加上极小负数（如 `-1e9` 或 `-inf`），经 `softmax` 后权重接近 `0`，从而避免模型把无意义的 `[PAD]` 当作真实语义。


2. **特殊 Token 的完整性**：
* 编码器模型通常会在首尾添加 `[CLS]` 和 `[SEP]`；截断时需确保特殊标记不被意外破坏，且 `[PAD]` 位置不能参与有效池化（如 Mean Pooling 时需用 `attention_mask` 加权求平均）。


3. **填充方向（右侧 Padding vs. 左侧 Padding）**：
* **编码器模型（如 BERT）** 与 **训练阶段** 常用右侧 Padding；
* **解码器模型（如 GPT / LLM）做批量自回归推理（Batch Generation）** 时，通常需要**左侧 Padding（Left Padding）**，使所有序列的最后一个有效 token 对齐在最右侧，便于从同一位置继续逐 token 生成。

### 四、 常见坑点与工程建议

| 维度 | 潜在问题 | 工程建议 |
| --- | --- | --- |
| **截断位置选错** | 多轮对话或长上下文用默认右截断，把最新问题或关键结尾切掉 | 对话/最新输入优先考虑左截断或先保核心段再截断 |
| **全局固定长 Padding** | 多数短句被硬补到 `512` 或 `2048`，大量算力浪费在 `[PAD]` 上 | 训练与批推理优先使用动态填充（如 `DataCollatorWithPadding`） |
| **池化忽略 attention_mask** | 直接对 `last_hidden_state` 求均值，把 `[PAD]` 向量算进去 | 句向量池化务必结合 `attention_mask` 屏蔽填充位 |
| **LLM 批推理右 Padding** | 生成式模型批推理用右 Padding 会导致对齐错位 | 批量自回归生成时注意将 `tokenizer.padding_side = "left"` |
| **截断阈值设置过小** | 阈值过小导致大量关键信息丢失，影响准确率 | 先统计语料 token 长度分布（如 P95 / P99 分位数），再定 `max_length` |
