Constraining Generated Output Content.py代码进一步演示了如何利用 Hugging Face `transformers` 在生成过程中施加**内容限制与停止控制**，具体涵盖三类手段：**自定义字符串停止条件（`StoppingCriteria`）**、**词表禁用词黑名单（`bad_words_ids`）**，以及**前置主题提示引导（Pre-prompt Topic Steering）**。

---

### 一、 核心组件与模块拆解

#### 1. 自定义停止条件：`StringStoppingCriteria`

```python
class StringStoppingCriteria(StoppingCriteria):

    def __init__(self, stop_string, tokenizer, prompt_length):
        self.stop_string = stop_string
        self.tokenizer = tokenizer
        self.prompt_length = prompt_length

    def __call__(
        self, input_ids: torch.LongTensor, scores: torch.FloatTensor, **kwargs
    ) -> bool:
        generated_text = self.tokenizer.decode(
            input_ids[0][self.prompt_length :], skip_special_tokens=True
        )
        return self.stop_string in generated_text

```

* **为什么不用固定 Token ID 做停止？** 原生的 `eos_token_id` 只能针对词表中的特殊结束符；而业务中往往希望遇到特定**字符串或标点**（如 `"。"`、`"\n\n"`、`"</answer>"`）就停下来。同一段字符串在不同分词器或子词切分下，Token 边界可能不固定，直接解码新生成片段后做子串判断更直观。
* **执行时机**：在 `model.generate()` 的每一步自回归解码结束、决定是否继续下一个 Token 时调用 `__call__`。一旦返回 `True`，生成循环就会提前终止。
* **注意 `input_ids[0]**`：当前写法默认处理 `batch_size=1` 的单条样本；如果扩展为多条批量生成，需要按批次逐条判断是否全部满足停止条件。

#### 2. 禁用词黑名单：`bad_words_ids`

```python
bad_words_ids = []
if bad_words:
    for word in bad_words:
        ids = tokenizer(word, add_special_tokens=False).input_ids
        if ids:
            bad_words_ids.append(ids)

```

* **工作原理**：`transformers` 的 `NoBadWordsLogitsProcessor` 会在每一步解码前检查已生成序列的后缀。若某个候选 Token 拼接上去后会凑出 `bad_words_ids` 中的禁用词序列，就会将其 Logit 设为负无穷（屏蔽选择），从而阻止该词出现。
* **`add_special_tokens=False`**：禁用词是片段级限制，必须关闭 BOS/EOS 等特殊标记，否则编码出的 ID 序列无法匹配正常生成过程中的子串。

#### 3. 停止符后的精准裁剪

```python
if stop_token and stop_token in generated_text:
    generated_text = generated_text.split(stop_token)[0] + stop_token

```

* `StoppingCriteria` 是在某个 Token 生成后触发停止的，解码出的文本可能已经包含了停止符，甚至极少数情况下多带了紧随其后的字符。通过 `split(stop_token)[0] + stop_token` 可以把输出干净地截断在第一个 `stop_token` 处。

#### 4. 主题引导生成：`generate_with_topic`

```python
def generate_with_topic(prompt, topic_words, max_new_tokens=80, temperature=0.7):
    topic_prompt = f"【主题：{'、'.join(topic_words)}】{prompt}"
    return generate_text_with_constraints(
        topic_prompt, max_new_tokens=max_new_tokens, temperature=temperature
    )

```

* 这是一种典型的**输入侧软约束（Prompt 引导）**：在原始问题前拼接结构化主题标签（如 `【主题：智能家居、人工智能】`），借由自回归注意力机制把上下文拉向目标领域。
* **软约束特征**：它能显著提高相关词汇和语境的出现概率，但属于**概率引导而非硬性拦截**——模型仍有可能顺着续写习惯发散到相邻话题。

### 三、 工程实践中的关键细节与潜在坑点

* **`bad_words_ids` 的绕过与副作用**：
* **同义/谐音/拆分绕过**：黑名单只能挡住完全匹配的 Token 序列（如 `"战争"`），无法阻止 `"交战"`、`"干戈"`、`"战乱"` 或加标点/空格拆分后的变体。
* **误伤无辜词**：如果某个禁用词恰好是常用词的一部分，或模型被迫绕开它时，局部句式可能显得略别扭；在生产环境中，黑名单通常只作**解码层辅助防线**，语义合规与敏感内容仍需配合输出审核模型或后处理校验。


* **每步解码的性能开销**：
* `StringStoppingCriteria` 每次生成新 Token 都会调用一次 `tokenizer.decode(...)`。当 `max_new_tokens` 较大或并发较高时，频繁解码会有一定 CPU/Python 侧开销；若只需按单个固定 Token 停止，直接判断最后一个 Token ID（`input_ids[0, -1] == stop_token_id`）会更快。


* **基座模型的指令遵循局限**：
* `uer/gpt2-chinese-cluecorpussmall` 是纯续写型预训练模型，不是对话对齐模型。面对 `【主题：...】未来的生活将如何改变？` 这类问句，它更倾向于“接着往下写一段类似文本”，而不是像现代 Instruct/Chat 模型那样直接给出条理分明的回答。
