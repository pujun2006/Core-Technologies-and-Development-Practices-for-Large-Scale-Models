Batch Processing and Parallel Acceleration for Generative Models.py代码基于 Hugging Face `transformers` 与中文 GPT-2 模型（`uer/gpt2-chinese-cluecorpussmall`），实现了一个支持**分批调度（Mini-batch）**、**左填充对齐**、**`DataParallel` 兼容**以及**新生成 Token 截取**的批量文本生成脚本。

下面按模块拆解代码逻辑、关键工程细节，以及代码切片与多卡封装中值得注意的坑点。

---

### 一、 分步代码解析

#### 1. 设备检测、左填充分词器与 `pad_token` 配置

```python
device = "cuda" if torch.cuda.is_available() else "cpu"

model_name = "uer/gpt2-chinese-cluecorpussmall"
tokenizer = AutoTokenizer.from_pretrained(model_name, padding_side="left")
model = AutoModelForCausalLM.from_pretrained(model_name)

if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token

model.to(device)

```

* **`padding_side="left"`**：自回归因果语言模型（Causal LM）在批量生成时，必须把填充符放在**左侧**，使批次中所有样本的有效输入结尾对齐在同一列，后续才能在相同位置向后追加新 Token。
* **`pad_token` 对齐**：GPT-2 类分词器通常没有独立 `pad_token`，将其设为 `eos_token` 可避免批处理填充时报错或缺失填充 ID。

#### 2. 分批切割与张量编码

```python
for i in range(0, len(prompts), batch_size):
    batch_prompts = prompts[i : i + batch_size]

    inputs = tokenizer(
        batch_prompts,
        return_tensors="pt",
        padding=True,
        truncation=True,
    ).to(device)

```

* 将总列表按 `batch_size`（此处设为 `2`，3 条提示词会分成 `2 + 1` 两个批次）切片送入模型，控制单次前向的显存峰值；
* `padding=True` 会把当前批次内较短的句子在左侧补齐到该批次最大长度，并生成 `attention_mask`（有效 Token 为 `1`，填充位为 `0`）。

#### 3. `DataParallel` 兼容与 `generate()` 调用

```python
raw_model = model.module if hasattr(model, "module") else model

with torch.no_grad():
    output = raw_model.generate(
        input_ids=inputs.input_ids,
        attention_mask=inputs.attention_mask,
        max_new_tokens=max_new_tokens,
        top_k=top_k,
        top_p=top_p,
        temperature=temperature,
        do_sample=True,
        pad_token_id=tokenizer.pad_token_id,
        eos_token_id=tokenizer.eos_token_id,
    )

```

* **`raw_model` 提取**：若外层用 `torch.nn.DataParallel` 包装过模型，PyTorch 会把原模型挂在 `model.module` 下；由于 `DataParallel` 只封装了 `forward`，直接调 `model.generate(...)` 往往会找不到属性或出现行为异常，因此取出 `raw_model` 调用 `generate()` 是必要的兼容处理。
* **`attention_mask`**：必须显式传入，让模型在注意力计算中忽略左侧 `pad_token` 的干扰。

#### 4. 解码与拼接输出

```python
for j, out_ids in enumerate(output):
    input_len = inputs.attention_mask[j].sum().item()
    gen_ids = out_ids[inputs.input_ids.shape[1] :]
    text = tokenizer.decode(gen_ids, skip_special_tokens=True)
    generated_texts.append(batch_prompts[j] + text)

```

* 因为采用了**左填充**，批次中每条样本的原始输入结束位置都在同一列，即 `inputs.input_ids.shape[1]`；所以直接用 `out_ids[inputs.input_ids.shape[1] :]` 切片，就能精准取出**本轮新生成的 Token**，再解码后与原始 `batch_prompts[j]` 拼回完整文本。

### 三、 代码中的两个细节与工程改进建议

1. **`input_len` 计算了但未参与切片**
循环里写了 `input_len = inputs.attention_mask[j].sum().item()`，但真正切片时用的是 `inputs.input_ids.shape[1]`。在**左填充**下，用 `inputs.input_ids.shape[1]` 才是正确的起点（因为左侧还有 `pad_token` 占位）；`input_len` 仅代表有效 Token 数，若保留未用会让人误以为它被用来切片了，可清理或用于日志统计。
2. **多卡推理更推荐使用 `DDP` / 独立多进程或现代推理引擎，而非 `DataParallel**`
`torch.nn.DataParallel` 在单机多卡下存在主卡显存偏重、GIL 锁开销以及跨卡收集输出张量等瓶颈，训练和推理中通常更推荐 `DistributedDataParallel`（DDP）、`device_map="auto"` 或专用推理框架（视具体模型与部署环境而定）。
3. **补充 `model.eval()` 与 `repetition_penalty**`
推理前调用 `model.eval()` 可确保模型处于评估模式；在生成较长文本（如 `max_new_tokens=60`）时，适当加上 `repetition_penalty=1.1`（或 `no_repeat_ngram_size=2`）能进一步降低局部重复概率。
