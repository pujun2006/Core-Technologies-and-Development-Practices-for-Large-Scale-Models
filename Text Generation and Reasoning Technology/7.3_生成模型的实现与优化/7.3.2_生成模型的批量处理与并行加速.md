在生成模型（尤其是自回归大语言模型）的训练与推理中，批量处理（Batching）**与**并行加速（Parallelism）的核心目标是提升硬件利用率（GPU/NPU 算力与显存带宽），在满足延迟约束的前提下最大化吞吐量（Tokens/s）。

与常规分类或编码模型不同，自回归生成具有**动态输出长度**和**逐词解码（Decode）访存受限**的特点，因此批量与并行策略需要针对性设计。

---

### 一、 批量处理：从静态批处理到连续批处理

#### 1. 静态批处理（Static Batching）与 Padding 陷阱

在基础 PyTorch 推理或微调中，将多条样本拼成 `(Batch Size, Seq Len)` 张量一次性送入模型：

* **对齐要求**：自回归生成时，输入序列通常需要**左填充（Left Padding，`padding_side="left"`）**，使各条序列的最后一个有效 Token 对齐在同一列，方便统一向后追加新 Token 并正确切片提取生成结果。
* **静态批的短板**：
1. 批次内必须按最长序列对齐，短序列填充大量 `pad_token`，浪费计算与 KV Cache 显存；
2. 在解码阶段，只要批次中还有**最长的一条请求**未生成 `<EOS>` 或未达到最大长度，整批就不能释放槽位，先结束的序列只能空跑或闲置，造成明显“尾延迟”与算力碎片。



#### 2. 连续批处理（Continuous Batching / Iteration-level Batching）

现代推理引擎将批处理粒度从“整条请求周期”细化到**单次前向迭代（Iteration）**：

* 某个请求一旦生成 `<EOS>` 或达到上限，立即移出当前活跃批次，腾出的槽位可在**下一个解码步**直接接纳队列中的新请求；
* 结合 **PagedAttention** 等非连续 KV Cache 内存管理机制，可大幅降低显存碎片并提高并发批大小。

如上图所示，左侧静态批处理中较早完成的序列会占用槽位等待整体结束，而右侧连续批处理在序列结束（`END`）后能快速复用空位接入新序列，显著提升 GPU 占用率与吞吐量。

### 二、 多维并行加速策略

当单卡显存装不下大模型、KV Cache 随并发/长上下文急剧膨胀，或单卡算力不足时，需要结合多维并行：

#### 1. 数据并行（Data Parallelism, DP / FSDP / ZeRO）

* **核心思路**：在多张卡上复制模型（或分片存储权重、梯度与优化器状态，如 FSDP / ZeRO-2 / ZeRO-3），每张卡处理不同的数据批次。
* **适用场景**：训练/微调阶段扩大全局 Batch Size；推理阶段若单卡能完整放下模型，通常采用多副本 DP（配合负载均衡）来线性提升并发吞吐，几乎没有层间张量通信开销。

#### 2. 张量并行（Tensor Parallelism, TP）

* **核心思路**：把单层内部的权重矩阵按行或按列切分到多张卡上（例如 Attention 的 $Q/K/V/O$ 投影与 FFN 的上下投影），每步前向传播中通过 `AllReduce` 集合通信合并结果。
* **适用场景**：单卡显存放不下超大模型，或需要**降低单条请求延迟**。由于每层都需要通信，TP 通常部署在节点内高速互联（如 NVLink）的卡之间，跨节点使用通信开销会明显放大。

#### 3. 流水线并行（Pipeline Parallelism, PP）

* **核心思路**：按网络层数将模型纵向切分为多个 Stage，分配到不同设备上依次执行前向与反向传播。
* **关键优化（Micro-batching）**：朴素流水线会产生严重的“气泡”（Bubble，设备等待上下游的时间）。将大 Batch 拆成多个更小的 **Micro-batch** 流水灌入，可显著缩小气泡比例。
* **适用场景**：跨机器/跨节点部署超大模型，通信频次低于 TP，但需注意流水线气泡与显存平衡。

#### 4. 序列并行（Sequence Parallelism, SP）与专家并行（EP）

* **序列并行（SP）**：在张量并行的基础上，对 LayerNorm / RMSNorm 与 Dropout 等非张量切分部分按序列维度拆分，进一步降低激活值显存占用，常用于长上下文训练/推理。
* **专家并行（Expert Parallelism, EP）**：针对 MoE（混合专家）模型，将不同专家子网络分布到不同设备上，Token 经路由器（Router）分发到对应专家计算后再聚合。

### 三、 推理侧的补充加速手段

除了批处理与多维并行，生成模型推理还常叠加以下协同加速技术：

1. **Prefill 与 Decode 分离（PD 分离）**
* **Prefill** 阶段计算密集、算力利用率高；**Decode** 阶段每步只算 1 个新 Token，主要受限于读取历史 KV Cache 的显存带宽。将两者拆分到不同实例或调度池，可减少互相干扰、稳定首字延迟（TTFT）与每 Token 延迟（TPOT）。


2. **前缀缓存（Prefix Caching / Prompt Cache）**
* 当多个请求共享相同的 System Prompt、Few-Shot 样例或长文档前缀时，直接复用已计算好的前缀 KV Cache，省去重复 Prefill 计算。


3. **投机解码（Speculative Decoding）**
* 用小模型（Draft Model）或轻量草稿头快速生成 $K$ 个候选 Token，再由目标大模型一次性并行验证并按概率接受合法前缀，在保持输出分布不变的前提下加速逐词生成。

### 四、 选型与工程权衡总结

| 场景 / 目标 | 推荐策略 | 关注重点 |
| --- | --- | --- |
| **本地脚本 / 离线小批量测试** | 左填充 `Batch` + `torch.inference_mode()` + `max_new_tokens` | 注意 `padding_side="left"` 与显存上限 |
| **高并发线上服务** | 连续批处理 + KV Cache 分页管理 + 前缀缓存 | 平衡首字延迟（TTFT）、吞吐量与显存水位 |
| **单卡装不下 / 低延迟要求高** | 节点内张量并行（TP）+ 量化（如 FP8/INT4） | 控制 `AllReduce` 通信开销与精度回退 |
| **超大规模模型 / 超长序列** | TP + PP / FSDP + 序列并行（SP）或 MoE 专家并行（EP） | 减少流水线气泡、通信瓶颈与显存峰值 |
