Static and Dynamic Quantization.py代码使用 PyTorch 的 **`torch.ao.quantization`**（Eager 模式量化 API），对比了同一个三层全连接网络（`SimpleFCN`）在 **Float32 基线**、**动态量化（Dynamic Quantization）** 与 **静态量化（Static Quantization）** 下的 CPU 推理耗时。

下面按模块逐一拆解其原理、作用及工程细节。

---

### 一、 模型定义与 `QuantStub` / `DeQuantStub`

```python
class SimpleFCN(nn.Module):
    def __init__(self):
        super(SimpleFCN, self).__init__()
        self.quant = quantization.QuantStub()
        self.dequant = quantization.DeQuantStub()
        self.fc1 = nn.Linear(784, 256)
        ...

```

* **`QuantStub` 与 `DeQuantStub` 的作用**：在 PyTorch Eager 模式**静态量化**中，模型外部输入通常仍是高精度张量（如 `float32`），最终输出也往往需要恢复为高精度张量。`QuantStub` 会在前向传播入口处将浮点输入转换为量化张量（`qint8` / `quint8`）；`DeQuantStub` 则在出口处把量化结果反量化回浮点型。
* **为什么动态量化不需要它们？** `quantize_dynamic` 只对指定的层（这里是 `nn.Linear`）在算子内部临时完成激活值的动态量化与反量化，因此不需要在模型前后显式放置转换桩。
* **算子融合提示**：在更复杂的实际模型中，常会把 `Linear + ReLU` 融合为单个算子以减少中间读写和反量化次数；当前代码保留了独立的 `ReLU` 层，逻辑更直观，但少了一层算子融合优化。

### 二、 推理计时函数 `test_inference`

```python
def test_inference(model, input_data, description=""):
    with torch.no_grad():
        for _ in range(10):
            _ = model(input_data)

    start = time.time()
    with torch.no_grad():
        for _ in range(100):
            output = model(input_data)
    end = time.time()
    print(f"{description} 推理时间: {(end - start):.4f} 秒")

```

* **预热（Warm-up，10 次循环）**：首次运行模型时，CPU 缓存未命中、线程初始化或首次算子调度会产生额外开销。先跑 10 次预热，能避免首轮抖动干扰正式计时。
* **`torch.no_grad()`**：推理阶段关闭梯度计算与计算图构建，节省内存并减少不必要的开销。
* **计时粒度**：对 `(1024, 784)` 的输入连续执行 100 次前向传播，统计总耗时。若要看单次或单样本延迟，可将总时间除以 `100`（单次前向）或 `100 * 1024`（单条样本均摊）。

### 三、 三种推理模式对比

#### 1. 原始 Float32 模型

```python
model = SimpleFCN().to("cpu")
model.eval()
input_data = torch.randn(1024, 784)

```

* **必须调用 `model.eval()**`：量化前将模型切到推理模式，禁用 Dropout、BatchNorm 统计更新等训练态行为，确保观察器（Observer）与算子转换行为符合推理预期。
* **放至 CPU**：代码中明确 `.to("cpu")`，因为 PyTorch 原生的 `torch.ao.quantization`（`fbgemm` / `qnnpack` 后端）主要面向 x86 和 ARM CPU 的低比特指令优化。

#### 2. 动态量化（Dynamic Quantization）

```python
dynamic_model = quantization.quantize_dynamic(
    model, {nn.Linear}, dtype=torch.qint8
)

```

* **行为特点**：
* 仅对 `{nn.Linear}` 层生效，权重提前量化为 `qint8`（8-bit 有符号整数）。
* 每次前向传播到达 `Linear` 层时，**实时计算当前激活张量的缩放因子（Scale）与零点（Zero-point）**，动态量化激活值后进行低比特矩阵计算，再按需反量化。


* **适用与局限**：无需校准集，接入成本最低；但每次前向都要在线统计最值和计算量化参数，在矩阵尺寸较小或运行时统计占比高时，加速幅度可能有限。

#### 3. 静态量化（Static Quantization）四步法

```python
static_model.qconfig = quantization.get_default_qconfig("fbgemm")
prepared_model = quantization.prepare(static_model)
# 校准前向传播
quantized_model = quantization.convert(prepared_model)

```

1. **设置 `qconfig`（指定量化配置与后端）**：
* `get_default_qconfig("fbgemm")` 选用面向 x86 服务器/桌面 CPU 的默认量化配置（权重通常为逐通道对称量化，激活常为非对称量化）；若是 ARM / 移动端设备，通常对应 `"qnnpack"`。
* 实际使用时，通常还需配合 `torch.backends.quantized.engine = "fbgemm"`（或 `"qnnpack"`）确保底层量化引擎一致。


2. **`prepare`（插入观察器 Observer）**：
* 遍历模型并插入统计节点，用于记录各层激活值的分布范围（如最小值、最大值等）。


3. **`Calibration`（校准）**：
* 用 10 个 batch（每批 `128 x 784`）做前向传播，让 Observer 收集激活值范围。
* **关键注意点**：这里用的是 `torch.randn` 随机噪声做校准，仅用于跑通流程；**真实业务中必须使用贴近真实输入分布的代表性校准集**，否则静态固定的量化参数会导致严重截断误差或精度下降。


4. **`convert`（转换为真实量化算子）**：
* 根据校准统计结果算出固定的 Scale 和 Zero-point，移除 Observer，将浮点模块替换为真正的量化算子（如 `QuantizedLinear`）。

### 五、 补充实践建议

* **同时评估精度与速度**：量化会引入数值舍入与截断误差，测速的同时务必对比量化前后模型在验证集/测试集上的准确率或输出误差，避免“变快了但精度不可用”。
* **线程与环境控制**：CPU 推理耗时受 `torch.get_num_threads()`、后台负载和 CPU 睿频影响较大，正式对比建议固定线程数并多次重复测试取稳定结果。
