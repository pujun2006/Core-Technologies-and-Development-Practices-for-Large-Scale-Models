**跨机器多 GPU（多节点多卡，Multi-Node Multi-GPU）分布式训练**，是指在多台物理服务器（节点）上各自挂载多张 GPU，通过节点内高速互联（如 NVLink / NVSwitch）**与**节点间网络（如 InfiniBand / RoCE / 以太网）协同执行同一份训练任务。

相比单机多卡，跨机训练不仅涉及进程组与张量/模型切分，还必须处理**网络可达性与端口配置、跨节点集合通信后端调优、多机环境变量与启动编排、数据与共享存储一致性**以及**节点故障容错**。

---

### 一、 核心环境变量与网络通信配置

在 PyTorch 分布式训练（尤其是使用 `torchrun` 或标准 `dist.init_process_group` 时），多台机器上的进程需要通过一组核心参数建立全局视角与 rendezvous（会合）连接：

| 配置项 / 环境变量 | 含义与作用 | 跨机配置要点 |
| --- | --- | --- |
| **`NNODES`（节点总数）** | 参与本次训练的总机器数（例如 `2` 台机器则为 `2`） | 各节点必须填写完全一致的总节点数 |
| **`NODE_RANK`（当前节点编号）** | 当前机器的节点索引（`0` 到 `NNODES - 1`） | 每台机器必须唯一且正确对应（主节点通常为 `0`） |
| **`NPROC_PER_NODE`（单机进程/卡数）** | 每台机器启动的训练进程数（通常等于单机可用 GPU 数） | 节点间可相同或按实际配置，总 `WORLD_SIZE` 为各节点进程数之和 |
| **`MASTER_ADDR`（主节点地址）** | `NODE_RANK=0` 所在机器的可达 IP 或主机名 | 必须是所有其他节点**能直接连通**的网卡 IP，不能写死成各机自己的 `127.0.0.1` / `localhost` |
| **`MASTER_PORT`（会合端口）** | 主节点用于建立初始通信握手的空闲 TCP 端口 | 需确保防火墙放行且未被其他服务占用 |
| **`WORLD_SIZE`（全局总进程数）** | 整个集群参与训练的总 Rank 数量 | 等于各节点进程数总和；全局 `RANK` 范围为 `0` 到 `WORLD_SIZE - 1` |

#### 网卡与 NCCL 网络环境变量

跨机通信时，若机器配备多张网卡（如管理网口、普通以太网口、InfiniBand / RoCE 网卡），必须明确指定通信接口或后端参数，否则可能走错网卡导致带宽极低甚至超时失败：

* **指定 Socket / Gloo 网卡**：当涉及控制面或 Gloo 后端时，可通过 `GLOO_SOCKET_IFNAME` 指定高带宽内网网卡名（如 `eth0`、`ib0` 等，避免误走 Docker 网桥或低速管理口）。
* **NCCL 网络与 IB/RoCE 控制**：在 GPU 跨机通信中，常见调优项包括指定网卡（`NCCL_SOCKET_IFNAME`）、在无 InfiniBand 或特定网络环境下按需配置 `NCCL_IB_DISABLE`、以及开启调试日志（如 `NCCL_DEBUG=INFO` 用于排查建连与拓扑问题）。

### 二、 跨机启动与编排方式

在生产环境中，跨机多卡训练通常使用 **`torchrun`**（或由 Slurm / Kubernetes 等集群调度器调用 `torchrun`）在各个节点上分别拉起本地多进程：

```bash
# 在节点 0 (MASTER_ADDR=10.0.0.1) 上执行（假设每机 8 卡）
torchrun \
  --nnodes=2 \
  --node_rank=0 \
  --nproc_per_node=8 \
  --master_addr=10.0.0.1 \
  --master_port=29500 \
  train.py

# 在节点 1 上执行
torchrun \
  --nnodes=2 \
  --node_rank=1 \
  --nproc_per_node=8 \
  --master_addr=10.0.0.1 \
  --master_port=29500 \
  train.py

```

#### 代码层面的关键规范

1. **不要在代码里硬编码 `MASTER_ADDR` / `MASTER_PORT` 覆盖环境变量**：当使用 `torchrun` 或集群调度器注入环境变量时，代码内若强行写 `os.environ["MASTER_ADDR"] = "localhost"` 会破坏多机连接。
2. **使用 `LOCAL_RANK` 绑定本地 GPU**：每个进程应读取环境变量 `LOCAL_RANK`（`0` 到 `nproc_per_node - 1`）调用 `torch.cuda.set_device(local_rank)`，而全局 `RANK` 则用于分布式采样器、日志/Checkpoint 守卫或进程组划分。
3. **进程组后端选择**：跨机 GPU 通信首选 `"nccl"`；若包含 CPU 参与或特定网络调试场景，可按需配置进程组或后端。

### 三、 跨机并行策略与拓扑对齐

跨机训练时，**机内带宽**通常远高于**机间带宽**。如果并行切分策略与物理拓扑错配，跨机通信会迅速拖慢整体吞吐：

1. **机内优先承接高频通信（如 TP / 机内分片）**：张量并行（TP）每层都可能涉及 `AllReduce` 或 `AllGather`，一般控制在单机（如 8 卡）内部，利用 NVLink/NVSwitch 高带宽；部分框架也会在机内做更密集的局部聚合。
2. **跨机合理组合 DP / ZeRO / FSDP 与 PP**：
* **DDP / ZeRO-1 / ZeRO-2**：梯度或优化器状态同步相对规整，适合跨节点扩展数据并行规模。
* **PP（流水线并行）**：Stage 边界仅做点对点激活/梯度传递，通信量相对可控，适合跨节点拉长模型深度（需配合足够的 Micro-Batch 减少流水线气泡）。
* **ZeRO-3 / FSDP 跨机**：每次前反向都需要跨机 `AllGather` 权重分片，对跨节点带宽要求较高，需评估网络带宽是否足以支撑。


3. **注意全局 Batch Size 与学习率缩放**：跨机增加节点数往往意味着全局 Batch Size 变大（`global_batch = micro_batch * local_batch * world_size * grad_accum_steps`）。批量增大后，通常需要相应调整学习率、Warmup 步数或梯度裁剪策略以维持收敛稳定。

### 四、 数据、存储、时间同步与容错管理

#### 1. 数据集与 `DistributedSampler`

* 各节点必须能访问到相同的训练数据集（可通过共享存储挂载、对象存储流式读取或各节点预先同步同一份数据分片实现）。
* 使用 `DistributedSampler(dataset, num_replicas=world_size, rank=rank, shuffle=True)`，并在每个 Epoch 开始前调用 `sampler.set_epoch(epoch)`，确保所有节点、所有 Rank 拿到互不重叠且随 Epoch 轮换的数据子集。

#### 2. Checkpoint 保存与共享文件系统

* **保存路径**：若各节点挂载了共享存储（如 NFS / Lustre / 并行文件系统），多 Rank 同时写同一个文件路径会导致冲突损坏，通常只在全局 `rank == 0` 保存完整权重，或按规范写入各自独立的分片文件/目录；若各节点只有本地磁盘，则需注意权重分散在不同机器上，后续汇总或恢复时需有明确的收集/加载机制。
* **Checkpoint 频率**：跨机训练涉及多台机器与网络设备，单次训练耗时较长，建议定期保存 Checkpoint，便于故障后从最近检查点恢复，而不是从头重跑。

#### 3. 常见跨机故障与排查方向

* **初始化超时（Timeout / Rendezvous 失败）**：检查 `MASTER_ADDR` 是否可达、`MASTER_PORT` 是否被占用或防火墙拦截、各节点的 `NNODES` / `NODE_RANK` / `WORLD_SIZE` 是否一致，以及系统时钟/网络连通性是否正常。
* **运行中途卡死（Hang）**：多半是因为某个节点或某个 Rank 触发异常提前退出、数据加载卡住或条件分支导致部分 Rank 漏掉一次 `dist` 通信。可通过开启分布式日志、设置合理超时时间以及逐节点检查进程存活状态来定位。
* **跨机吞吐远低于预期**：重点排查是否误走了低速网卡（`NCCL_SOCKET_IFNAME` / `GLOO_SOCKET_IFNAME`）、是否存在跨机高频细粒度通信（如跨机 TP 或过重的分片同步），以及各节点算力/数据读取是否均衡。
