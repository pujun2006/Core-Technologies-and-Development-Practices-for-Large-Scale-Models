大模型在多 GPU 上的并行处理实现，本质上是围绕**进程组（Process Group）划分**、**张量/模块切分与通信调度**、**显存生命周期管理**以及计算与通信重叠（Overlap）展开的系统工程。在现代训练框架（如 PyTorch `torch.distributed` / FSDP / Megatron-LM / DeepSpeed 等）中，单一并行往往不够，通常会把多种并行维度正交组合起来运行。

下面从**多维并行组合方式**、**核心实现机制**与**工程落地关键点**三个层面详细说明多 GPU 并行处理是如何实现的。

---

### 一、 多 GPU 并行维度的组合实现

在大模型场景下，假设总 GPU 数为 $N$，常见做法是将全局通信域拆分为多个正交的子进程组（Process Group），分别承担不同的并行维度：

1. **状态分片数据并行（ZeRO / FSDP）**
* **实现逻辑**：各 DP Rank 只保存自己负责的那一份**优化器状态、梯度或模型参数分片**。在前向传播进入某个模块/层之前，通过 `AllGather` 收集完整权重执行计算，算完立即释放非本 Rank 负责的分片；反向传播时再 `AllGather` 权重算梯度，随后通过 `ReduceScatter` 归约并把各自对应的梯度分片留在本地更新。
* **作用**：在不改变数据并行扩展吞吐的前提下，大幅削减单卡静态显存占用。



2. **层内张量并行（TP，常配合序列并行 SP）**
* **实现逻辑**：将单个 Transformer 层的权重矩阵按列或按行切分到 TP 组内的多张 GPU 上。例如 MLP 的第一层线性变换按列切分（各卡输出一部分隐藏维度，无需立刻通信），第二层线性变换按行切分（各卡输入对应切片做局部矩阵乘，最后通过 `AllReduce` 汇总结果）。
* **配合序列并行（SP）**：对于 `LayerNorm` / `RMSNorm` 或 Dropout 等未被 TP 切分的激活，可沿序列维度（Sequence）切分存储，在进入 TP 切分的线性层前做 `AllGather`、离开后做 `ReduceScatter`，进一步降低长序列激活显存。
* **实现约束**：由于每层都要通信，TP 组大小通常等于单机 GPU 数（如 8 卡），依赖机内 NVLink/NVSwitch 高速互联。


3. **跨层流水线并行（PP）**
* **实现逻辑**：将模型的若干连续层划分为一个 Pipeline Stage，分配给 PP 组中的不同 GPU（或节点）。训练时把一个全局/局部 Batch 拆成多个更小的 **Micro-Batch**，按调度策略（如 **1F1B** 或交错流水）依次推进前向与反向。
* **通信方式**：相邻 Stage 之间通过点对点通信（如 `Send` / `Recv` 或 `P2P` 算子）传递前向激活与反向梯度，而非全局集合通信。


4. **上下文并行（CP）与专家并行（EP）**
* **上下文并行（CP）**：面向超长上下文训练，将输入序列按块拆分到不同卡上，结合分块/环形注意力（如 Ring Attention 思路）在块间流转 KV 块与局部注意力统计量，避免单卡保存完整长序列注意力状态。
* **专家并行（EP）**：面向 MoE（Mixture of Experts）模型，将不同专家子网络放置在 EP 组内的不同 GPU 上；Token 经过路由（Router）打分后，通过 `AllToAll` 通信分发到对应专家计算，再通过 `AllToAll` 聚合回原 Token 位置。

### 二、 底层实现机制：通信域、调度与重叠

#### 1. 多维进程组（DeviceMesh / ProcessGroup）管理

多 GPU 并行并不是把所有卡混在一个全局 `AllReduce` 里，而是需要为每个并行维度建立独立的通信组：

* 例如在 `DP × PP × TP` 组合中，同一 TP 组内的卡共享张量切分通信，同一 PP 组内的卡构成流水线阶段，同一 DP 组内的卡承担数据分片与梯度同步。
* 在 PyTorch 现代生态中，常通过类似 `DeviceMesh` 的抽象把多维 GPU 映射为逻辑网格，按维度切片创建对应的 `ProcessGroup`，避免通信域错乱。

#### 2. 计算与通信重叠（Communication-Computation Overlap）

多 GPU 吞吐能否跑满，很大程度上取决于**通信时间能否被计算时间掩盖**：

* **独立通信流（Stream）**：将通信操作放在独立的 CUDA Stream 上发起，使其与计算 Stream 并行执行，减少同步阻塞。
* **分桶与流水交织**：
* 梯度同步常按梯度桶（Bucket）在反向传播逐层完成时尽早触发，让后面层的反向计算与前面梯度桶的通信并行。
* 流水线并行通过拆分 Micro-Batch，在早期 Micro-Batch 反向计算的同时推进后续 Micro-Batch 的前向或通信，压缩空闲气泡。



#### 3. 启动与环境编排

* 生产环境通常使用 `torchrun`（替代早期的手写 `mp.spawn` 样板逻辑）启动多进程训练，自动注入 `RANK`、`LOCAL_RANK`、`WORLD_SIZE` 等环境变量，并支持弹性扩缩容与故障重启。
* 每个进程绑定一张本地 GPU（`cuda:{local_rank}`），使用 `nccl` 等后端执行底层集合通信与点对点传输。

### 三、 工程落地时的关键调优与排障要点

1. **先算显存账，再定切分优先级**：
* 显存不够时，先区分是**静态模型状态（权重+梯度+优化器）**超限，还是**动态激活值**超限。
* 静态显存紧张优先看 ZeRO / FSDP 分片与 TP/PP 切分；动态激活紧张则结合 Activation Checkpointing、Micro-Batch 大小调整、序列/上下文切分或融合注意力算子。


2. **严格对齐通信拓扑与带宽层级**：
* 高频细粒度同步（如 TP、`AllToAll`）尽量落在**机内高速互联**；跨节点链路优先承载带宽需求相对更易调度的 PP 或分片/数据并行通信，并关注跨机网络拥塞。


3. **关注负载均衡与尾延迟**：
* 在 PP 中，各 Stage 层数或算力耗时不均会导致流水线卡在最慢 Stage；在 EP 中，路由分配不均（Token 集中打向少数热门专家）会导致部分卡计算与 `AllToAll` 通信过载，需配合负载均衡辅助损失或容量限制策略。


4. **Checkpoint 保存/加载与数值一致性**：
* 多维并行下，权重与优化器状态可能分散在多个 Rank 或多个分片文件中，保存与恢复时需明确分片布局（Sharding Spec），确保跨不同并行配置恢复或推理导出时权重拼装正确。
