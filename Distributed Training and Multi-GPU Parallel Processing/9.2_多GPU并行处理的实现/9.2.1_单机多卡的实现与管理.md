**单机多卡**是指在同一台物理服务器（或虚拟机）上挂载多张 GPU（常见如 2 卡、4 卡或 8 卡），通过**多进程架构 + 集合通信（NCCL / Gloo）+ 硬件拓扑感知管理**协同完成训练或推理。

在单机范围内，所有 GPU 共享同一台机器的 CPU、系统内存（RAM）与本地存储，卡间通常通过 **NVLink / NVSwitch** 或 **PCIe Switch** 互联。把单机多卡跑稳、跑快，关键在于**进程与设备绑定、数据与参数同步、硬件拓扑对齐以及日常运行与排障管理**。

---

### 一、 进程架构与设备绑定实现

#### 1. 推荐采用“一卡一进程（1 Process per GPU）”

在 PyTorch 工程中，单机多卡训练应优先使用**多进程**（如通过 `torchrun` 启动，或在测试脚本中使用 `torch.multiprocessing.spawn`），而不是单进程多线程的 `nn.DataParallel`：

* 每个进程拥有独立的 Python 解释器与 GIL，避免多线程锁竞争带来的调度瓶颈。
* 每个进程通过 `LOCAL_RANK`（`0` 到 `N-1`）绑定到一张独立的 GPU（如 `torch.cuda.set_device(local_rank)`），显存分配与 CUDA Context 隔离更清晰。

#### 2. 进程组初始化与可见卡控制

* **环境变量与启动器**：使用 `torchrun --nproc_per_node=<卡数> train.py` 启动时，框架会自动注入 `RANK`、`LOCAL_RANK`、`WORLD_SIZE`、`MASTER_ADDR` 与 `MASTER_PORT`，无需手写脆弱的进程拉起样板代码。
* **卡号隔离（`CUDA_VISIBLE_DEVICES`）**：当机器上部分卡被占用或只想用指定卡时，可通过 `CUDA_VISIBLE_DEVICES=0,1,2,3` 限制可见设备。需注意：**被屏蔽后，脚本内看到的 `local_rank` 是相对可见卡列表重排后的 `0..K-1**`，务必注意物理卡号与逻辑索引的对应关系。

### 二、 训练与推理中的核心协同机制

#### 1. 数据分发与随机种子管理

* **数据切分（`DistributedSampler`）**：训练时应为数据集配置 `DistributedSampler`，确保不同 Rank 拿到互不重叠的样本子集，避免多卡重复算同一批数据；每个 Epoch 开始前调用 `sampler.set_epoch(epoch)` 保证打乱顺序随轮次变化。
* **随机数种子控制**：若涉及数据增强、Dropout 或随机采样，需为不同 Rank 设置差异化但可复现的种子（如基于 `base_seed + rank`），既避免各卡随机掩码完全趋同，又保证实验可复现。

#### 2. 并行策略与显存管理协同

单机多卡常见实现方式包括 **DDP**、**FSDP / ZeRO**，以及在单机高速互联下的 **张量并行（TP）** 或 **流水线并行（PP）**：

* **DDP**：每卡持有完整模型副本，反向传播时通过梯度分桶与 `All-Reduce` 同步梯度，适合模型能放进单卡显存、追求高吞吐的场景。
* **FSDP / ZeRO**：将优化器状态、梯度或参数分片分布在单机多卡上，按需 `AllGather` / `ReduceScatter`，适合单卡显存装不下完整模型状态的情况。
* **机内张量并行（TP）**：单机内卡间带宽高时，可将大矩阵乘按行/按列切分到多张卡协作，降低单卡权重与激活压力。
* **结合 AMP 与 Checkpoint**：在单机多卡上配合 `torch.amp.autocast`（`FP16` / `BF16`）与激活重计算（`torch.utils.checkpoint`），能进一步压低激活显存并提升计算吞吐。

#### 3. 只有主进程（`rank == 0`）执行的动作

多进程同时执行时，全局性副作用必须做 Rank 守卫，否则会出现文件覆盖、日志刷屏或竞争损坏：

* **保存 Checkpoint / 导出模型**、**写 TensorBoard / 实验监控日志**、**打印汇总指标**，通常只由 `rank == 0`（或局部主进程）执行；保存分布式分片权重时，则按框架规范在所有参与 Rank 上协同保存对应的分片状态。

### 三、 硬件拓扑与运行期管理

#### 1. 关注机内互联拓扑与 NUMA / CPU 亲和性

* **NVLink vs. PCIe**：卡间存在 NVLink 直连或 NVSwitch 时，`All-Reduce`、`AllGather` 等高频通信吞吐显著高于仅走 PCIe 的卡对；若跨 PCIe Root Complex 或跨 CPU Socket（NUMA 节点）通信，延迟和带宽会出现明显差异。
* **排查工具**：可用 `nvidia-smi topo -m` 查看 GPU 互联拓扑与亲和关系，用 `nvidia-smi` 或 `nvtop` 观察各卡显存占用、GPU 利用率与功耗/温度是否均衡。

#### 2. 常见死锁、卡死与显存异常管理

* **集合通信死锁（Hang）**：只要有一个 Rank 提前退出、报错跳过 `dist` 集体操作，或因数据长度不均导致部分 Rank 少走一次前反向/通信，其余 Rank 就会在 `All-Reduce` / `barrier` 处无限等待。排查时应检查各 Rank 分支逻辑是否一致、异常是否被吞掉，并合理设置超时机制。
* **显存碎片与残留进程**：训练异常中断后，偶尔会有僵尸 Python 进程占着 GPU 显存不释放；需先清理残留进程，再评估是否因 Batch Size 过大、长序列激活堆积或未 `.detach()` 保留计算图导致 OOM。

### 四、 单机多卡工程检查清单

| 管理维度 | 关键检查点 | 常见风险 |
| --- | --- | --- |
| **进程与设备** | `local_rank` 与 `torch.cuda.set_device` 一一对应；使用 `torchrun` 管理生命周期 | 多卡抢占同一张卡或单进程 `DataParallel` 性能受限 |
| **数据与同步** | 使用 `DistributedSampler` 并按 epoch 调用 `set_epoch`；各 Rank 通信路径一致 | 重复训练相同样本、部分 Rank 少通信导致卡死 |
| **I/O 与日志** | 日志、单份权重保存与评估汇总做 `rank == 0` 控制 | 多进程同时写同一文件造成损坏或冲突 |
| **硬件与显存** | 结合 `nvidia-smi` / `nvidia-smi topo -m` 观察负载均衡，合理搭配 AMP / Checkpointing | 负载不均、显存 OOM 或残留进程占用显存 |
